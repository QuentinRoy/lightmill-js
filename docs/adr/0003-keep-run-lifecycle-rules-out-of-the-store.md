# Keep run lifecycle rules out of the store

`DataStore` is a published interface that other people can implement, and a Postgres store is expected. If the store enforced the rules for starting, resuming, completing, and canceling a run, every implementation would have to copy them. The SQLite store did this with database triggers that no other database can reuse. So `DataStore` is plain data access. It enforces only what any database states natively and atomically: foreign keys, unique log numbers within a log sequence, and unique run names among runs that aren't canceled. Reads work anywhere. Every write goes through `withTransaction`, which is serializable or fails with `TRANSACTION_CONFLICT`. An internal server module reads the run inside that transaction, applies the lifecycle rules with a pure decision step, and writes the result.

The cost is that code calling the store directly can write any status and gets no rejection, so the rules protect a run only when the change goes through the server. We considered one atomic "update this run" store method that checks every rule and returns a typed rejection, and one store method per transition. Both leave each implementation to rewrite the transition table, the resume rule, and the completion rule, and the store is not ours to control.
