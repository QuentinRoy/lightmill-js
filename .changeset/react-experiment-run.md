Add `Run`, which starts or resumes a run, plays its timeline, sends each task's completion log and the logs from `useLogger` to the server and completes the run once every log is stored. Pass it a `@lightmill/log-client` client, `experimentName`, `runName`, a `timeline` (or `null` while the app loads it) and the task components in `elements.tasks`. `Run` plays the first timeline it gets once the run is ready, once per run. React Strict Mode neither starts nor resumes a run twice. Before the run starts, changing `client`, `experimentName` or `runName` selects another run. Once it has started, keep `Run` mounted until the run ends: mounting a new `Run` on it, or changing `client`, `experimentName` or `runName`, crashes the run with a `RUN_REMOUNTED` error and interrupts it, so a reload resumes it. `@lightmill/react-experiment` does not import `@lightmill/log-client` at runtime.

When a run with the same experiment and run names is ongoing, `Run` asks before resuming it. `useResumeRun()` returns `{ resume, run, lastLog }` for a custom `elements.resume`, where `lastLog` is the run's last completion log. `Run` resumes the run after its last completion log, so the task in progress restarts and its logs are canceled. It then reads every completion log of the run and replays the timeline: it asks the timeline for each completed task, without showing it, and passes back the task result from its completion log, so a generator that adapts to results, such as a staircase, gets back where the participant stopped. A task whose id or type differs from the completion log at the same step, or a timeline that ends before the last completed task, stops the run with a `TIMELINE_MISMATCH` error before any task shows, as does a task whose id is already used. Task results come back from the server as JSON, so a `Date` in a result comes back as a string. `elements.loading` shows while `Run` reads the logs and replays. With `dangerouslyAutoResume`, `Run` resumes without asking and shows `elements.loading` meanwhile. Use it in development only: in production, it would resume a run open in another tab or on another device without asking, and cancel the logs that run wrote after the resume point.

While logs cannot be delivered, `Run` shows `elements.paused`, whose default has a retry button and a link to download the logs that were not saved. `useLogDelivery()` returns `{ error, inFlightLogs, retry }` for a custom screen. It works in every element of `Run`, including `elements.loading`, `elements.resume` and `elements.error`. `retry` never rejects.

When the run cannot start or crashes (a task error, a throwing timeline, a `TIMELINE_MISMATCH`, a rejected `addLog` or `completeRun`, or a run that is interrupted or canceled after the timeline completed), `Run` shows `elements.error`. `useRunError()` returns the thrown value unchanged as `{ error }`. The slot renders outside `Run`'s own error boundary, so what it throws reaches the app's. The default tells the participant to contact the experimenter, explains `RUN_EXISTS`, `ONGOING_RUNS` and `RUN_REMOUNTED`, and has a collapsed block of details, the download link while logs are held and a retry button while delivery is paused.

After a crash, `Run` interrupts the run once every log is stored, so a reload lands on the resume prompt. If the logs cannot be stored, it tries again each time a retry stores them. An interrupt failure is logged and does not replace the error; a run left running resumes like an interrupted one. The browser asks for confirmation before the page unloads until the run ends, and while the error slot shows held logs.

`elements.loading`, `elements.resume`, `elements.paused`, `elements.error` and `elements.completed` have defaults.

The default `AnyLog` type, used when no log type is registered with `RegisterExperiment`, now has a string index signature instead of `PropertyKey`.
