The logger retries a batch of logs that fails with a network error, a timeout, a 5xx, a `408`, or a `429` (waiting for `Retry-After`), with jittered exponential backoff for up to 2 minutes. A request times out after `requestTimeout.base` milliseconds plus `requestTimeout.perKilobyte` milliseconds per kilobyte sent, a new `Client` option (defaults 10000 and 100). A batch the server rejects with `413` is resent in halves. Once retries run out or the server answers with another error, the logger pauses: the failed batch's `addLog()` promises reject, and every other in-flight log is held with its promise pending, never dropped. `Logger#inFlightLogs` lists them, and `Logger#retry()` sends them again. `Logger#state` (`idle`, `sending`, `retrying`, `paused`, or the ended run's status) and `Logger#subscribe()` report delivery and work with React's `useSyncExternalStore`. `flush()` now rejects only while logs it waits for are held, instead of rethrowing the first error forever. `completeRun()` rejects while logs are held; `cancelRun()` and `interruptRun()` do too, unless passed `{ discardInFlightLogs: true }`. The missing-log check of `flush()` and the request ending a run are retried the same way.
